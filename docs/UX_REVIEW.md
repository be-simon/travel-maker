# UX Review — Travel Maker (v0.3 기준)

| 항목 | 내용 |
|---|---|
| 검토 대상 | PRD v0.3, prototype.html v0.3 |
| 작성일 | 2026-07-18 |
| 방법론 | 화면별 휴리스틱 리뷰 + 유사 제품 리서치 근거 확인 |

## 방법론

7개 화면(홈·내 북마크·북마크(트립)·타임라인·지도·Today·개요)을 실제 사용 시나리오(계획 전/계획/여행 중)에 대입해 검토했다. 판단이 필요한 지점은 아래 5개 질의로 리서치해 근거를 확보했다.

1. 여행 앱의 지도 동선 시각화 — Wanderlog/Roadtrippers 패턴
2. CRDT 없는 실시간 협업의 충돌 피드백 관행
3. OCR 결과 확인/저장 UX 패턴 — Expensify SmartScan, Google Lens
4. 모바일 필드유즈(야외·한손·이동 중) UX 원칙
5. 북마크 중복 감지 UX — Raindrop.io

## 발견 사항

### 1. 북마크 중복 감지 없음 — P0
**문제**: 같은 장소를 링크로 한 번, OCR로 한 번 저장하면 조용히 중복 생성된다. 계정 단위로 누적되는 구조라 시간이 지날수록 문제가 커진다.
**근거**: Raindrop.io는 저장 시 URL(우리 경우 `place_id`)을 정규화해 비교하고, 이미 저장된 경우 "저장됨" 표시를 즉시 보여준다.[1]
**조치**: 3개 입력 경로(직접입력 제외 — place_id가 없는 수동 입력은 정확한 매칭이 불가능하므로 대상에서 제외) 모두에서 place_id 일치 시 "이미 저장된 장소입니다 → [기존 북마크 보기]"를 저장 직전에 표시.

### 2. 내 북마크에 텍스트 검색이 없음 — P0
**문제**: 계정 단위로 여러 여행에 걸쳐 누적되는 구조인데 필터 칩(국가/카테고리/출처)만 있고 검색이 없다. 북마크가 수십 개를 넘어가면 필터만으로는 특정 장소를 찾기 어렵다.
**조치**: "내 북마크" 화면 상단에 텍스트 검색 인풋 추가, 필터 칩과 AND 조건으로 결합.

### 3. OCR 확인 리스트가 이진 상태(매칭/불일치)만 제공 — P0
**문제**: 현재는 "매칭된 장소" 또는 "일치 없음" 두 가지뿐이다. 실제로는 "비슷한 후보가 여러 개라 사람이 골라야 하는" 중간 상태가 가장 흔하다.
**근거**: 좋은 OCR 확인 UX는 필드 단위 신뢰도를 노출하고 한 번의 탭으로 고칠 수 있게 한다("한 번의 탭 수정 vs 5단계 폼"이 좋고 나쁜 앱을 가른다).[3]
**조치**: 상태를 3단계로 확장 — 정확히 일치(자동 체크) / 후보 여러 개(드롭다운으로 선택) / 일치 없음(직접 입력 유도). 각 행 인라인 수정 가능.

### 4. 실시간 협업의 실행취소(Undo) 부재 — P0
**문제**: 타임라인은 이번에 Google Calendar식 자유 편집(드래그 생성/이동/리사이즈/삭제)이 추가됐다. 실수로 블록을 잘못 옮기거나 지우면 되돌릴 방법이 없고, 준실시간 동기화 때문에 실수가 즉시 동행자 화면에도 반영된다.
**조치**: 모든 블록 편집(생성/이동/리사이즈/삭제) 후 하단에 "변경됨 · 실행 취소" 토스트를 5초간 노출.

### 5. Last-write-wins 충돌의 무통보 데이터 손실 — P0
**문제**: F7의 정책(레코드 단위 last-write-wins)은 의도적으로 단순화한 선택이지만, 리서치 결과 이 방식의 알려진 실패 모드는 "한쪽 편집이 조용히 사라지고 아무 통보가 없어 사용자가 신뢰를 잃는 것"이다.[2]
**근거**: "간단한 last-write-wins 전략은 통보나 복구 경로 없이 한쪽의 편집을 조용히 버린다. 사용자는 작업을 잃고 신뢰를 잃는다."[2] 같은 자료는 토스트 알림이 이 문제의 효과적인 완화책이라고 명시한다.
**조치**: 내가 방금 편집한 블록을 다른 멤버의 변경이 곧바로 덮어쓰면 "OO님이 방금 이 일정을 수정했어요" 토스트로 알린다. CRDT 도입 없이 LWW의 가장 큰 리스크(무통보 손실)만 제거하는 저비용 대응.

### 6. 협업 프레즌스(누가 지금 보고 있는지) 표시 없음 — P0
**문제**: F7은 데이터 동기화만 다루고, "지금 하잉님도 이 화면을 보고 있다"는 신호가 없다. 신호가 없으면 5번 문제(충돌)가 실제로 자주 발생할 가능성이 커진다.
**조치**: 워크스페이스 헤더에 현재 같은 화면을 보고 있는 멤버 아바타를 표시(가벼운 presence, CRDT 불필요).

### 7. 지도에 동선(순서)이 없음, 흩어진 마커만 존재 — P0
**문제**: F5의 존재 이유가 "동선을 직관적으로 파악"인데, 현재는 마커만 찍혀 있고 순서가 보이지 않는다.
**근거**: Wanderlog는 방문 순서대로 마커를 선으로 연결해 보여주고, 마커 사이 예상 이동 시간·거리도 함께 표시한다 — "여행 계획의 혼돈을 명료하고 논리적인 순서로 바꿔준다"는 평가를 받는 핵심 기능이다.[4]
**조치**: 선택한 날짜의 확정 일정을 시간순으로 연결하는 옅은 선 + 번호 마커(①②③...) 추가.

### 8. 블록 간 이동시간 힌트 없음 — P0(경량 버전만)
**문제**: 타임라인에 스팟을 배치할 때 바로 앞 일정과 지리적으로 얼마나 떨어져 있는지 알 수 없어, 물리적으로 불가능한 일정을 짜기 쉽다.
**판단**: PRD 10장 Open Question에 "이동 시간 자동 계산(Directions API) 도입 여부 — 비용/복잡도 대비 가치 검증 필요"가 이미 있다. Directions API 자체는 여전히 Open Question으로 남기되, **좌표 기반 직선거리 계산**(신규 API·비용 없음, 클라이언트 계산만)으로 "약 15분 이동(직선거리 기준)" 같은 힌트를 우선 제공하는 경량 버전은 지금 추가한다. 실제 도보 경로와 다를 수 있음을 라벨로 명시해 오해를 방지한다.

### 9. Today 모드가 모바일 필드유즈 원칙을 완전히 따르지 않음 — P0
**문제**: 야외에서 한 손으로, 걸으면서 쓰는 화면인데도 주요 액션 버튼 위치·탭 타겟 크기가 명시적으로 검증되지 않았다.
**근거**: 스마트폰 사용자의 49%가 한 손으로 조작하며, 주요 액션은 화면 하단 40%(엄지 도달 영역)에 있어야 하고 탭 타겟은 최소 44×44pt여야 한다.[5]
**조치**: "지금 갈 만한 곳" 추천의 [+ 일정에 넣기] 버튼을 하단 고정 영역에 재배치, 탭 타겟 44px 이상 명시, 텍스트 대비 강화.

### 10. Today 모드에 "길찾기" 딥링크가 없음 — P0
**문제**: 추천 스팟을 일정에 넣은 다음, 실제로 거기까지 어떻게 가는지는 서비스가 답을 주지 않는다. PRD는 명시적으로 Directions API 자체 구현을 하지 않기로 했지만(Out of Scope), 네이티브 지도 앱으로의 딥링크는 API 비용이 전혀 들지 않는다.
**조치**: Today 추천 카드와 타임라인 블록 상세에 "Google Maps로 길찾기" 버튼 추가 (`google.com/maps/dir/?api=1&destination=...` 딥링크로 기기의 지도 앱 실행).

### 11. 여행 중(In-trip) 상태가 홈 화면에서 강조되지 않음 — P0
**문제**: 트립 카드는 "계획 중"/"완료" 두 상태만 있다. 여행 당일에 홈 화면을 열면 Today 모드로 가는 지름길이 없다 — 정작 이 서비스의 핵심 차별 기능이 가장 필요한 순간에 안 보인다.
**조치**: 여행 기간 안에 해당하는 트립 카드에 "여행 중" 배지 + Today 모드로 바로 가는 강조 CTA 추가.

### 12. 오프라인/최신성 신호 부재(Today 모드) — P0(최소 버전)
**문제**: PRD 10장 Open Question에 오프라인 캐시 범위가 이미 열려 있다. 완전한 캐싱은 P1로 남기되, 해외 데이터 끊김이 가장 흔히 일어나는 화면(Today)에서 "지금 보고 있는 정보가 최신인지"조차 알 수 없는 것은 신뢰 문제다.
**조치**: Today 모드 상단에 "마지막 동기화 N분 전" 같은 최신성 표시를 추가(완전한 오프라인 캐싱과 별개, 저비용 신뢰 신호).

### 13. 타임라인 빈 상태(empty state) 안내 없음 — P1
**문제**: 처음 타임라인을 열었을 때 사용법(드래그로 생성/북마크에서 끌어오기)을 설명하는 안내가 없다. 심각도가 낮아 P1로 분류.

## 반영 방침
1~12번은 신규 유료 API나 아키텍처 확장 없이, 기존 스택 안에서 클라이언트 로직·UI로 해결 가능하다고 판단해 이번에 PRD·프로토타입에 반영한다. 8번(이동시간)은 Directions API 도입 여부라는 기존 Open Question을 대체하지 않고, 그 경량 버전만 우선 반영한다. 13번은 P1로 남긴다.
