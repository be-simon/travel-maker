## 1. 개요/배경

**서비스명(가칭)**: Travel Maker

**한 줄 정의**: 여행별 워크스페이스를 만들어 후보 스팟 수집 → 시간대별 일정 배치 → 여행 중 실시간 일정 조정까지 하나의 도구로 해결하는 협업형 여행 계획 웹서비스.

**배경**: 현재 사용자들은 Google Sheets로 (a) 날짜×시간대 그리드 형태의 일정표와 (b) 도시별 후보 스팟 목록(영업시간, 입장료, 메모, 지도 스크린샷 포함)을 수작업으로 관리하고 있다. 이 방식에는 다음과 같은 문제가 있다.

- 지도와 일정이 분리되어 있어 동선을 확인하려면 스프레드시트와 지도 앱을 오가야 한다.
- 여행 중 모바일 환경에서 스프레드시트를 편집하기 어렵다.
- 현재 위치를 기준으로 "지금 갈 만한 곳"을 고르는 기능이 없어 즉흥적인 일정 변경이 번거롭다.
- 영업시간 등 스팟 정보를 매번 손으로 검색해서 입력해야 한다.

Travel Maker는 이 세 가지 문제(지도-일정 분리, 모바일 편집성, 위치 기반 추천 부재)를 하나의 웹 도구로 해결하는 것을 목표로 한다.

**목표 규모/용도**: 개인 및 지인 그룹을 위한 사이드 프로젝트다. 불특정 다수를 대상으로 하는 상용 서비스가 아니며, 인프라는 무료 티어 내에서 운영하는 것을 원칙으로 한다.

**플랫폼 전략**: 1차 목표는 모바일 대응 반응형 웹이다. 여행 중 사용성이 실제로 검증된 이후에 네이티브 앱으로 확장하는 것을 고려하며, 본 PRD에서는 이를 로드맵 항목으로만 언급한다.

## 2. 목표와 비목표 (Non-goals)

### 목표
- 여행 계획의 전 과정(후보 수집 → 일정 배치 → 여행 중 조정)을 스프레드시트 없이 하나의 서비스에서 처리한다.
- 지도와 일정을 한 화면에서 연결해 동선을 직관적으로 파악할 수 있게 한다.
- 여행 중에는 현재 일정 기준으로 다음 행동을 빠르게 결정할 수 있게 돕는다.
- 동행자 간 일정 변경이 준실시간으로 공유되게 한다.

### 비목표 (Out of Scope)
- 항공/숙소 예약 연동 및 결제 기능
- 네이티브 앱 (로드맵상 P2 이후 검토 대상이며 본 PRD의 개발 범위가 아님)
- 문자 단위 실시간 공동 편집(CRDT 기반 동시 편집)
- 수익화 기능(광고, 유료 플랜 등)

## 3. 사용자 시나리오

Travel Maker는 여행의 라이프사이클을 3단계로 정의하고, 각 단계에 맞는 화면과 기능을 제공한다.

| 단계 | 설명 |
|---|---|
| 1. 계획 전 (수집) | 여행 워크스페이스를 생성하고 동행자를 초대한다. 각자 가고 싶은 곳을 계정의 "저장한 장소"에 자유롭게 수집하고, 여행에 담는다. |
| 2. 계획 (배치) | 수집된 후보를 날짜×시간대 타임라인에 드래그해 일정을 확정하고, 지도로 동선을 확인하며 조정한다. |
| 3. 여행 중 (적응) | 현재 일정의 위치와 다음 확정 일정을 기준으로 갈 만한 후보를 추천받아 원탭으로 일정에 편입한다. 변경 사항은 동행자에게 준실시간으로 반영된다. |

### 3.1 화면 구조(IA)와 용어 — v0.5 재설계

여행 계획의 3단계를 화면으로 옮기되, 네비게이션을 **2단**으로 나눈다.

- **계정 레벨(여행 밖)**: `홈`(내 여행 목록), `저장한 장소`(개인 라이브러리). 로그인한 사용자 본인에게 귀속되며 특정 여행과 무관하다.
- **여행 레벨(여행 안)**: 홈에서 여행을 선택하면 워크스페이스로 진입한다. 여행명·기간·멤버를 담은 셸 아래 `플랜` · `Today` · `멤버` 서브탭을 가진다. 여행 화면은 반드시 여행에 진입해야 접근할 수 있다.

**통합 "플랜" 화면**: 후보 목록 · 타임라인 · 지도를 각각의 화면으로 분리하지 않고, 하나의 플랜 화면에 `장소 패널 │ 캔버스(타임라인 ⇄ 지도 토글)`로 함께 둔다. 왼쪽 장소 패널에서 후보를 고르고, 오른쪽에서 타임라인과 지도를 오가며 배치·확인한다. "지도와 일정이 분리되어 오가야 한다"는 원 문제(§1)를 화면 레벨에서 해소하기 위함이다.

**용어**: 계정 라이브러리는 **저장한 장소**(구 "내 북마크"), 여행에 담아 편집하는 작업본은 **장소**(구 "트립 북마크/스팟", 상태: 후보/배치/방문)로 부른다. 두 개념을 모두 "북마크"로 부르던 혼란을 없앤다. 데이터 모델의 `bookmarks`/`spots` 테이블(§7)은 각각 이 두 개념에 대응한다.

## 4. 기능 요구사항

### P0 (MVP)

**F1. 계정/인증**

- 왜 필요한가: 별도 회원가입 절차 없이 신뢰할 수 있는 신원(이메일)으로 워크스페이스 초대·권한 관리를 단순화하기 위함이다.
- 요구사항
  - Google OAuth 로그인만 지원한다 (별도 회원가입 없음).
  - 사용자 식별은 Google 계정 이메일을 기준으로 한다.

**F2. 여행 워크스페이스**

- 왜 필요한가: 여행 단위로 데이터와 협업 범위를 격리해야 여러 여행을 동시에 관리하거나 다른 동행자 그룹과 섞이지 않고 운영할 수 있다.
- 요구사항
  - 여행 단위 워크스페이스를 생성/수정/삭제할 수 있다 (이름, 기간, 대표 도시들).
  - 멤버 초대: 이메일(Google 계정) 입력 → 초대 링크 발송 → 해당 이메일로 로그인 시 자동 합류. 피초대자가 아직 가입 전이어도 초대는 pending 상태로 유지된다.
  - 권한은 Owner(워크스페이스 삭제·멤버 관리 가능)와 Editor(그 외 모든 편집 가능) 두 가지이며, MVP에서는 Viewer 권한을 두지 않는다.
  - 내 여행 목록을 보여주는 홈 화면을 제공한다.
  - 여행 생성 시 국가/도시를 선택하면, 계정의 저장한 장소 중 해당 국가/도시와 일치하는 것을 담을지 제안받는다(체크리스트에서 선택적으로 담기).
  - 여행 기간 중에는 홈 화면 트립 카드에 "여행 중" 배지가 표시되고, Today 모드로 바로 이동하는 CTA가 강조된다.

**F3. 저장한 장소 (계정 라이브러리 + 여행에 담기)**

- 왜 필요한가: 여행 준비는 한 번의 세션으로 끝나지 않고 몇 주에 걸쳐 스크린샷·링크·순간적인 발견이 쌓이는 과정이므로, 이 수집물이 특정 여행에 갇히지 않고 계정에 누적되어 다음 여행에서도 재사용될 수 있어야 한다.
- 요구사항
  - 저장한 장소는 여행이 아니라 계정 단위로 존재한다. 로그인한 사용자는 여행 워크스페이스와 무관하게 "저장한 장소" 라이브러리를 가진다. (내부적으로 개인 서랍이며, 여행 화면에서 "담기"로 꺼내 쓰는 소스로 동작한다.)
  - 장소 저장 시 3가지 입력 방법을 지원한다:
    1. **직접 입력**: 이름/카테고리/메모를 수동으로 입력 (Places 검색으로 자동 채움 가능, 기존과 동일)
    2. **Google 지도 링크**: 사용자가 구글맵 공유 링크(단축링크 포함)를 붙여넣으면, 서버(Edge Function)가 리다이렉트를 해석하고 Places API로 장소를 확정해 이름·주소·좌표·영업시간 미리보기를 보여준다. 사용자가 확인 후 저장한다(자동 신뢰하지 않음).
    3. **캡처 OCR**: 사용자가 스크린샷을 업로드하면 서버(Edge Function)가 OCR로 텍스트를 추출하고, 추출된 각 텍스트를 Places 검색으로 장소 매칭을 시도한다. OCR로 추출한 각 항목은 정확히 일치(자동 확인) / 후보 여러 개(선택 필요) / 일치 없음(직접 입력 유도) 세 가지 상태로 구분해 제시하며, 사용자가 각 항목을 인라인으로 확인·수정한 뒤 저장한다(OCR 노이즈가 많으므로 자동 저장하지 않음).
    4. (참고: 국가/도시별 자동 가져오기 흐름은 F2 참조)
  - 저장한 장소는 자동으로 국가/도시가 태깅된다(장소 좌표 기반 역지오코딩), 수동 수정 가능.
  - 저장하기 전 place_id 기준으로 계정에 이미 저장된 장소인지 확인하고, 중복이면 저장 대신 기존 항목으로 안내한다.
  - 저장한 장소 화면은 필터 칩 외에 텍스트 검색을 제공한다.
  - 저장한 장소를 여행에 담으면(F2의 가져오기 또는 플랜 화면의 장소 패널에서 개별 추가) 여행 전용 **장소** 레코드가 생성된다. 이 레코드는 원본(저장한 장소)의 **복사본**이며, 여행 안에서 메모/우선순위/비용/상태를 자유롭게 편집해도 원본은 변하지 않는다. (계정 라이브러리를 여러 여행에서 서로 다른 맥락으로 재사용하기 위함)
  - 여행의 장소(플랜 화면 좌측 패널)의 필드·상태 라이프사이클(후보/배치됨/방문완료), 우선순위 ★, 도시 그룹, 숙소 별도 관리는 기존 그대로 유지한다.

**F4. 타임라인 플래너**

- 왜 필요한가: 기존 스프레드시트 일정표와 동일한 날짜×시간대 그리드 멘탈 모델을 유지해 사용자의 학습 비용을 낮추면서, 드래그앤드롭으로 편집 효율을 높이기 위함이다.
- 요구사항
  - 통합 "플랜" 화면의 한 뷰로 제공된다: 좌측 장소 패널과 나란히 배치되고, 지도 뷰와 토글로 전환된다(§3.1).
  - 날짜(열) × 시간대(행) 그리드 뷰를 제공한다.
  - 플랜 화면 좌측 장소 패널에서 장소를 골라 시간 슬롯에 배치하고, 블록의 시작/종료 시각을 조절해 길이를 바꿀 수 있다.
  - 블록 타입은 스팟 / 이동(교통편 메모) / 숙소 / 자유 메모 네 가지이며 타입별로 색상을 구분한다.
  - 도시 단위로 상단 그룹핑을 표시한다 (예: 밀라노 2박, 피렌체 2박).
  - 모바일에서는 일 단위 세로 리스트 뷰로 전환된다.
  - 캘린더형 편집을 지원한다: 빈 시간 슬롯을 드래그해 새 블록을 생성하고(15분 단위 스냅), 기존 블록을 드래그해 같은 날짜 안에서 시간을 이동하며, 블록 가장자리를 드래그해 길이를 조절한다.
  - 블록을 클릭하면 전체 화면 이동 없이 인라인 팝오버로 제목·타입·시간·메모를 즉시 편집하고 삭제할 수 있다.
  - 같은 시간대에 겹치는 블록은 겹쳐 가리지 않고 나란히 배치한다.
  - 날짜를 넘는 드래그 이동은 MVP 범위에서 제외한다(팝오버의 날짜 변경으로 대체) — 가로 스크롤 그리드에서 크로스데이 드래그는 구현 복잡도 대비 가치가 낮다고 판단.
  - 블록 생성/이동/리사이즈/삭제 직후 실행 취소가 가능한 토스트를 노출한다.
  - 연속된 두 블록 사이의 이동 시간을 좌표 기반 직선거리로 추정해 참고 힌트로 표시한다(실제 도보 경로와 다를 수 있음을 명시). 정확한 경로/이동시간 계산(Directions API 도입)은 10장 Open Questions에 별도로 남아 있다.

**F5. 지도 뷰**

- 왜 필요한가: 텍스트로만 나열된 스팟 목록으로는 동선의 효율성을 판단하기 어렵기 때문에, 지리적 분포를 시각적으로 확인하고 그 자리에서 일정에 추가할 수 있어야 한다.
- 요구사항
  - 통합 "플랜" 화면의 한 뷰로 제공된다: 타임라인 뷰와 토글로 전환되며, 좌측 장소 패널은 두 뷰가 공유한다(§3.1).
  - Google Maps JavaScript API를 임베딩한다.
  - 후보(회색 계열)와 확정 일정(색상)을 구분하는 마커를 사용하고, 우선순위 스팟은 강조 표시한다.
  - 날짜별 / 도시별 / 카테고리별 필터를 제공한다.
  - 마커 클릭 시 스팟 상세 카드와 "일정에 추가" 액션을 노출한다.
  - 특정 날짜를 선택하면 그날의 확정 일정을 시간순으로 연결하는 선과 순번(①②③...)을 표시해 동선을 한눈에 볼 수 있게 한다. 날짜를 특정하지 않으면(전체) 순서가 모호하므로 동선 선을 표시하지 않는다.

**F6. 여행 중 모드 (Today 뷰) — 핵심 차별 기능**

- 왜 필요한가: 여행 중에는 미리 짠 일정이 틀어지기 쉬운데, 위치 권한 없이 일정 맥락(현재 일정의 위치)과 남는 시간만으로 "지금 갈 만한 곳"을 즉시 제안하는 것이 기존 스프레드시트 방식으로는 불가능했던, 이 서비스의 핵심 차별점이다.
- 요구사항
  - 오늘 날짜 자동 포커스: 현재 시각 기준 현재 일정과 다음 일정을 함께 표시하고, 다음 일정까지 남은 시간을 표시한다.
  - "지금 갈 만한 곳" 추천: 현재 일정(진행 중 블록, 없으면 fallback 기준점)의 위치를 기준으로, 미방문 후보를 (a) 기준점에서의 거리, (b) 다음 확정 일정까지 남은 시간, (c) 영업시간(현재 영업 중 여부) 기준으로 필터·정렬한다.
  - 기준점 fallback: 진행 중 일정이 없으면 현재 시각 이전 마지막 일정 블록의 위치, 그것도 없으면 당일 숙소 위치를 사용한다.
  - GPS(Geolocation)는 MVP에서 사용하지 않는다 — 위치 권한 요청 없이 동작하며, 일정 데이터만으로 추천이 가능하다.
  - 추천 스팟은 원탭으로 오늘 일정의 빈 슬롯에 삽입할 수 있다.
  - 일정 밀림에 대응하기 위해 블록 시간을 빠르게 변경할 수 있는 UI(드래그 또는 ± 버튼)를 제공한다.
  - 추천 스팟과 타임라인 블록 상세에는 기기의 지도 앱으로 바로 연결되는 "길찾기" 딥링크를 제공한다(자체 경로 계산 기능 구현 없이 외부 지도 앱에 위임).
  - 주요 액션 버튼은 한 손 조작을 고려해 하단 영역에 배치하고 탭 타겟은 44px 이상으로 한다.
  - 화면 상단에 마지막 동기화 시점을 표시해 현재 보고 있는 정보의 최신성을 알 수 있게 한다.

**F7. 준실시간 동기화**

- 왜 필요한가: 여러 동행자가 각자의 기기에서 동시에 계획을 수정하는 협업 도구이므로, 한 사람의 변경이 새로고침 없이 다른 사람 화면에 반영되어야 계획이 어긋나지 않는다.
- 요구사항
  - 멤버가 후보/일정을 변경하면 다른 멤버 화면에 새로고침 없이 수 초 이내 반영된다.
  - 동시 편집 충돌은 행(레코드) 단위 last-write-wins로 처리한다. 문자 단위 공동 편집(CRDT)은 도입하지 않는다 — 개인/지인 규모에서는 동시 충돌 빈도가 낮다고 판단했기 때문이다.
  - 같은 워크스페이스를 보고 있는 멤버를 아바타로 표시한다(프레즌스).
  - 내가 방금 편집한 항목을 다른 멤버의 변경이 곧바로 덮어쓰면 "OO님이 방금 이 항목을 수정했어요" 토스트로 알린다. last-write-wins 정책의 무통보 데이터 손실 리스크를 완화하기 위함이다.

### P1 (MVP 이후)

- PWA 설치 지원 + 오늘 일정 오프라인 읽기 캐시
- 체크리스트(준비물), 비용 정산 메모
- 지난 여행 템플릿 복제
- Viewer 권한(읽기 전용 공유 링크)
- 주변 인기 장소 추천 — 후보에 없는 장소를 Google Places 인기 데이터 기반으로 추천
- GPS 기반 현재 위치 보조 사용(일정과 실제 위치가 다를 때 기준점 보정)
- 타임라인 빈 상태 안내(온보딩 힌트)

### Out of Scope (명시적 제외)

- 항공/숙소 예약 연동, 결제
- 네이티브 앱 (로드맵상 P2 이후)
- 실시간 문자 단위 공동 편집
- 수익화 기능

## 6. 아키텍처

| 영역 | 선택 |
|---|---|
| 프론트엔드 | Next.js (App Router) + TypeScript + Tailwind CSS + shadcn/ui. 드래그앤드롭은 dnd-kit 사용. |
| 백엔드/DB | Supabase — Postgres, Auth(Google OAuth), Realtime(postgres_changes 구독으로 준실시간 동기화), RLS(Row Level Security)로 워크스페이스 멤버만 데이터에 접근하도록 DB 레벨에서 격리. |
| 호스팅 | Vercel (프론트), Supabase 클라우드 (백엔드). 둘 다 무료 티어로 운영. |
| 지도 | Google Maps JavaScript API + Places API (New) |
| 서버리스 함수 | Supabase Edge Functions — Google 지도 링크 리다이렉트 해석(CORS 회피 목적, 클라이언트에서 직접 호출 불가), 캡처 OCR 처리 오케스트레이션에 사용. 이 두 함수를 제외하면 서비스 전체가 관리형 컴포넌트로만 구성된다는 원칙은 유지된다. |
| OCR | Google Cloud Vision API — 텍스트 추출. 이미 Google Maps Platform을 사용 중이므로 API 키/과금 관리 표면을 하나로 유지할 수 있고, 한글+영문 혼합 텍스트 인식 정확도가 클라이언트 WASM 대안보다 높다. |

**선정 이유**: 이 스택을 선택한 가장 큰 이유는 별도의 애플리케이션 서버를 운영하지 않고도 인증, 데이터베이스, 실시간 동기화라는 세 가지 핵심 인프라를 Supabase 한 서비스로 해결할 수 있기 때문이다. 특히 권한 로직(워크스페이스 멤버만 접근 가능)을 애플리케이션 코드가 아니라 RLS를 통해 DB 레벨에 위임함으로써 구현이 단순해지고 보안 경계가 명확해진다. 또한 Next.js/Vercel/Supabase 조합은 개인 프로젝트 규모의 트래픽에서 전 구간을 무료 티어로 운영할 수 있어, "무료 인프라 내 운영"이라는 제품 목표와도 부합한다. 다만 Cloud Vision은 무료 사용량(월 1,000유닛)을 초과하면 종량제 비용이 발생하는 유일한 컴포넌트이므로, 사용량 모니터링이 필요하다.

### 동기화 설계

- 클라이언트는 trip 단위로 Supabase Realtime 채널을 구독한다.
- 변경은 즉시 DB에 write되고, postgres_changes 이벤트를 통해 전 멤버에게 push된다.
- 충돌은 레코드 단위 last-write-wins로 처리한다. updated_at 비교가 별도로 필요하지 않으며, DB에 반영된 순서가 곧 최종 상태가 된다.
- 북마크는 계정 소유자 본인만 읽고 쓸 수 있으며(RLS), 트립 멤버 간 공유 대상이 아니다. 트립에 가져와 스팟으로 복사된 이후부터 해당 트립 멤버들에게 공유된다.

## 11. 경쟁 환경 분석 — AI 에이전트(ChatGPT/Claude)와의 차별화

**핵심 질문**: "ChatGPT나 Claude에게 '이탈리아 2주 일정 짜줘'라고 하면 되는데, 왜 별도 서비스가 필요한가?"

이 질문을 그대로 받아들이면 이 서비스는 존재 이유가 없다. 챗봇은 '생성'을 잘하고, Travel Maker는 애초에 생성 경쟁을 할 필요가 없다. 진짜 질문은 "여행 계획이라는 일이 대화 스레드 위에서 얼마나 잘 굴러가는가"이다. 답은 "구조화·협업·공간 판단·즉시 대응이 필요한 순간부터는 잘 굴러가지 않는다"이며, Travel Maker는 정확히 그 지점을 대체한다.

**1. 지속되는 구조 vs 휘발되는 대화**

챗봇의 산출물은 긴 텍스트 블록 하나다. 3주 뒤 "5/16 몇 시에 뭐였지"를 확인하려면 스크롤하거나 다시 질문해야 한다. 구조화된 레코드(날짜·시간·상태)가 없으면 필터링·정렬이 불가능하다. Travel Maker는 처음부터 DB 레코드이므로 "영업시간 지난 곳만", "확정 안 된 후보만" 같은 질의가 필터 클릭 한 번이다. 챗봇 산출물은 1회성 문서, Travel Maker는 살아있는 운영 도구다. 이번에 추가된 계정 단위 북마크(다음 여행에서도 재사용)는 이 축을 더 강화한다.

**2. 동시 협업**

챗봇 공유는 근본적으로 단일 스레드다. 동행자가 동시에 각자 후보를 추가하고 실시간으로 서로의 변경을 보는 것은 대화형 UI가 설계되지 않은 문제다. F7의 준실시간 동기화는 채팅으로 흉내낼 수 없는 다중 사용자 상태 관리다.

**3. 공간·시간 UI 패러다임**

지도와 캘린더 그리드는 보고 판단하는 인터페이스다. 텍스트 스레드는 선형적이라 "이 날 동선이 겹치나?"를 한눈에 볼 수 없고, 매번 사람이 텍스트를 파싱해 머릿속에서 그려야 한다. Today 모드처럼 "지금 위치·시간 맥락에서 다음 행동"은 화면을 켜면 바로 보이는 것과, 매번 챗봇에게 "나 지금 시에나야, 어디 갈까" 타이핑하는 것 사이의 마찰 차이가 결정적이다.

**4. 캡처의 저마찰성**

이번에 설계한 북마크 3종 입력이 정확히 이 지점을 겨냥한다. 인스타 스크린샷을 보다가 "여기 가고 싶다" 싶은 순간, 챗봇 창에 이미지를 올리고 "이거 기억해줘" 부탁하면 대화가 길어질수록 챗봇이 그걸 놓치거나 형식이 흐트러진다. 전용 캡처→OCR→확인→저장 플로우는 실패 모드가 없다.

**5. 사실 신뢰성**

영업시간·주소·예약 링크처럼 틀리면 여행이 망가지는 정보는 LLM이 생성한 텍스트보다 Google Places 같은 grounded 데이터에서 가져오는 편이 안전하다. 챗봇 일정표는 종종 없는 식당을 만들어내거나 오래된 영업시간을 말한다.

**6. 에이전트가 잘하는 일 — 거기서는 싸우지 않는다**

"이 도시에서 뭘 봐야 하지", "이 골목의 문화적 배경이 뭐야" 같은 오픈엔디드 리서치·브레인스토밍은 챗봇의 강점이며 Travel Maker가 재현할 이유가 없다. 전략적 결론은 경쟁이 아니라 파이프라인의 다른 단계를 맡는 것이다: 챗봇은 아이디어 발산, Travel Maker는 수집·구조화·협업·운영. 이 경계를 제품에 명시적으로 반영하면(예: 향후 "챗봇 대화 붙여넣기 → 북마크 자동 추출" 같은 가벼운 4번째 입력 경로), 에이전트를 경쟁자가 아니라 상류 소스로 흡수할 수 있다. 단, 현재 스코프에는 포함하지 않으며 P1 후보로만 남긴다.

**리스크 및 대응**: 챗봇 제품들도 점차 아티팩트·캔버스 형태로 구조화된 UI를 낼 수 있게 되는 추세다. 따라서 Travel Maker의 방어선은 "UI를 그릴 수 있는가"가 아니라, "지속되는 계정 단위 데이터 소유(북마크 축적) + 검증된 위치 데이터 + 다중 사용자 실시간 동기화"의 결합에 있다. 이 결합은 범용 대화형 에이전트가 구조적으로 재현하기 어려운 지점이다.

**결론**: Travel Maker는 "여행 계획을 생성하는 도구"가 아니라 "여러 명이 여러 주에 걸쳐 계획을 축적하고, 실시간으로 조율하고, 여행 중에 즉시 운영하는 durable·spatial·multiplayer 레이어"로 포지셔닝한다. 생성 경쟁은 하지 않는다.
